# Production releases and application data

Production requires an Organization Admin to confirm an Accepted commit. One production operation can run per Project. The database reservation pins the latest deployment attempt; concurrent or stale requests fail before CI starts. The live baseline commit and URL come from the same latest published deployment, including a failed operation whose code was published. A failed attempt before publication does not replace that live identity.

A deployment URL is publication evidence. Success also requires a saved migration review, a saved data recovery point, a rendered marker for the exact production commit, an application journey, resuming writes, and another application journey after writes resume. Failures after publication retain the production URL. The history shows failed releases even when their code is live.

## Application integration

The Accepted repository must define all six scripts below. Missing scripts stop the release before data capture or deployment. Existing Projects must add and test these scripts before their next production release. Sylph executes them in Cloudflare CI, with automatic command retries disabled.

These are trusted application integration hooks. The default Worker+D1 template can use the provider-backed adapter in `packages/cloudflare-recovery`; see its README for the supported writer/storage boundary, encrypted secret versions, required provider drill, and failure reconciliation. Other application boundaries must supply their own tested integration. Sylph validates and persists their receipts and enforces ordering. The application must implement and test actual provider backup, restore, inventory, migration checks, write coordination, and journeys. A receipt does not independently prove that a provider backup is restorable. Do not implement a hook that only prints a receipt.

| Script                  | Required behavior                                                                                                                                                                                                                                                                                                                                                                                |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `sylph:release:review`  | Inspect migrations, infrastructure and deployment scripts between the baseline and target commits. Test compatibility against the current schema, including earlier-code redeployments. For data recovery, check the target code against the selected restored schema. Exit nonzero if compatibility is unknown or unsafe. Do not mutate production.                                             |
| `sylph:release:prepare` | Pause all application writers, including scheduled jobs and queue consumers; drain in-flight writes. Inventory every stateful resource and required secret version. Capture coordinated recovery points while writers remain paused. Include an undo point even when the operation is itself a restore. Confirm backup availability and a previously tested restore procedure for each resource. |
| `sylph:release:restore` | Restore every resource in `SYLPH_RECOVERY_POINT` while writes remain paused. Check backup expiration and availability again before each restore. Restore secret versions through the configured secret store. Verify the restored resources and print the restore receipt only after all succeed.                                                                                                |
| `sylph:deploy`          | Deploy the selected commit while maintaining the write pause. Print `SYLPH_PRODUCTION_URL=https://...`.                                                                                                                                                                                                                                                                                          |
| `sylph:release:verify`  | Run the application's production journey against `SYLPH_PRODUCTION_URL`. Assert the full checkpoint and production identity, authenticate a dedicated test actor, exercise application data, verify expected results, and clean up test records. During the write pause, use a narrowly scoped verification path. This runs again after writes resume.                                           |
| `sylph:release:resume`  | Resume all writers only after the first journey passes. Be idempotent for operator recovery. Failure must return nonzero.                                                                                                                                                                                                                                                                        |

All release hooks receive `SYLPH_RELEASE_ID`, `SYLPH_PROJECT_ID`, `SYLPH_PROJECT`, `SYLPH_CHECKPOINT`, `SYLPH_DEPLOYMENT=production`, `SYLPH_BASE_COMMIT` (empty for the first release), and `SYLPH_RECOVERY_POINT` (empty for an ordinary release). Verification and resume also receive `SYLPH_PRODUCTION_URL`. Cloudflare credentials are supplied to the provider operations; journeys receive no explicit Cloudflare credential binding. `BETTER_AUTH_SECRET` is supplied to deployment. Hooks must obtain other application secrets from the configured secret store, never from receipt fields.

Receipt schemas live in `packages/domain/src/deployments.ts`. Print exactly one JSON receipt on one stdout line under each required marker. Timestamps are Unix milliseconds. Use full Git commit IDs and the IDs supplied in the environment.

- `SYLPH_MIGRATION_REVIEW`: `{ deploymentId, commit, baseCommit, compatible: true, evidence }`. Evidence identifies the compatibility checks and results, without secrets.
- `SYLPH_RECOVERY_POINT`: `{ deploymentId, projectId, commit, baseCommit, capturedAt, expiresAt, writesPaused: true, inventoryComplete: true, resources }`. Each resource has `{ id, kind, backupRef, restoreVerifiedAt }`. Kinds are `database`, `object-storage`, `kv`, `durable-object`, `secret`, or `other`. Include secret version references, not values. References must be opaque identifiers, never credentials or signed download URLs. Use the earliest expiration across all resources. An empty resource list is valid only after inventory confirms the application is stateless. Capture must be fresh (within 15 minutes), unexpired, and saved before publishing. Before saving it, Sylph refreshes provider identities and checks that the receipt covers exactly every existing owned stateful application resource, including retained retired data. Newly reserved resources with no provider identity do not yet contain application state. Recovery-control resources remain outside application restore. Secret snapshots are verified separately by the application integration because secret bindings are not individual resource-registry entries.
- `SYLPH_DATA_RESTORED`: `{ deploymentId, recoveryDeploymentId, commit, restored: true, resources }`. Resources must list every `kind:id` from the selected recovery point exactly once, with no extras. Missing or partial restore evidence blocks code publication.
- `SYLPH_PRODUCTION_JOURNEY`: `{ deploymentId, commit, url, passed: true, journeys }`. The nonempty journey list describes what was exercised. A URL or a homepage health check alone is not an application journey.

The application must render a visible element with `data-sylph-checkpoint` equal to the full commit and `data-sylph-deployment="production"`. Cloudflare Browser Run waits for this marker and stores screenshot and accessibility evidence before the first journey.

## Recovering code and data

Use **Recover code and data** on a deployment's saved recovery point. The confirmation shows the paired code commit and capture time, and requires acknowledgement that later writes can be lost. The server checks Admin access, Accepted commit identity, Project ownership, expiration, and the selected recovery point again. Recovery is a new deployment operation with its own undo point and evidence. No restore runs automatically after a failed release.

**Redeploy** applies earlier code to current data; it does not restore data. The same migration compatibility and backup requirements apply. After a release fails once data capture starts, ordinary redeployment is blocked because data or writer state can be uncertain. An Admin must select a valid recovery point. If capture failed before any usable point was saved, an operator must reconcile the application and writer state using its provider recovery procedure; do not clear the failure just to bypass the gate.

If restore, publication, or verification fails before resume, the application must retain its write pause. A resume failure may be partial; the second journey can also fail after writes have resumed. Inspect the saved failure and application writer state before selecting another recovery point. Expired points cannot be selected for restore. CI command retries are disabled because repeating a restore can discard additional writes; individual hooks must handle partial provider failures explicitly.

## Repository export scope

The version 2 repository manifest supplies temporary Git access and repository heads. It explicitly excludes application data, secret values, and Workspace runtime state (messages, running agents, pending operations, and Durable Object storage). It is not a full Workspace backup. Application recovery points appear separately in Deployment history. Backups of the Sylph control plane itself require a separate operator procedure.

## Rollout and verification

The initial schema in `packages/db/migrations/0001_initial.sql` includes release receipts and an index that permits one queued/running deployment per Project. This baseline requires fresh resources; it does not upgrade earlier experimental databases.

Local pipeline tests simulate CI, Browser Run, and provider receipts against SQLite. They cover ordering, incompatible migrations, missing/expired/unsaved backups, incomplete restores, mismatched journey commits, writer resume failures, and verification failures after publication. They do not prove a real provider backup or live restoration. Before production rollout, test the application's hooks in an isolated stage with real data, concurrent writers, a deliberate migration failure, complete restore, and a verified production journey. Production deployment and destructive restores require separate explicit approval.
